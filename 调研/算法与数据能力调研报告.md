# 单店健身房管理系统：算法与数据能力调研报告

> 对象：Spring Boot 3.2.5 + MySQL 8 + MyBatis-Plus 3.5.7 单店系统
> 已有模块：会员卡、课程、排课、预约签到、体测、器材、统计报表
> 调研日期：2026-10
> 结论口径：一切方案必须能在**单机 MySQL + 单进程 Spring Boot** 上跑通，不引入中间件（Redis/MQ/搜索/推荐平台）也能落地。

---

## 0. 先定标尺：单店的数据量到底有多少

所有选型错误都来自"把连锁的数据规模套到单店上"。先量化本项目量级：

| 维度 | 单店估计 | 说明 |
|---|---|---|
| 有效会员 | 300 ~ 1500 人 | 社区店 300-600，商圈店 800-1500 |
| 在售课程 | 10 ~ 25 门 | `course` 表行数 |
| 每周排课 | 20 ~ 45 节 | `course_schedule` 年增 1000-2300 行 |
| 日预约 | 30 ~ 120 条 | `reservation` 年增 1-4 万行 |
| 会员年预约量 | 每人 20 ~ 80 条 | 中位数约 35 |
| 并发峰值 | 同时 30 ~ 80 人抢课 | 热门课放课瞬间，持续 10 秒 |

由此得到三条硬约束，贯穿全文：

1. **行数级别 10^4，任何全表扫描都在 50ms 内**。不需要缓存层、不需要预聚合、不需要 OLAP。
2. **单用户样本 20-80 条，单物品（课程）样本 50-500 条**。这个量级下统计量（均值/中位数/占比）噪声大但可用，**矩阵分解、协同过滤的相似度不可用**。
3. **并发是"尖峰"不是"持续"**。MySQL 单行更新锁 1-2ms，理论上限 500-1000 TPS，实际需求 <100 TPS。**数据库层面完全扛得住，不需要 Redis 预扣**。

### 0.1 当前 schema 的数据缺口（会影响第 6 节指标）

从 `src/main/resources/db/schema.sql` 看，现有 12 张表存在 4 个结构性缺口，做指标前必须先补字段，否则指标算不出来或者算错：

| 缺口 | 影响的指标 | 处置 |
|---|---|---|
| 只有课程签到（`reservation.check_in_time`），**没有自由训练入场记录** | 到店率、月活、坪效人效全部失真——只上团课的会员会被统计进来，纯器械训练会员完全缺失 | 新增 `checkin_log(id, member_id, checkin_type, checkin_time, source)`，团课签到与闸机/前台入场都写这张表 |
| **没有门店面积字段** | 坪效无法计算 | `sys_config` 或新建 `gym_info(area_sqm)` |
| **没有私教课/私教订单** | 私教转化率、课消率无法计算 | 短期用 `course_type='PT'` + `card_type` 区分；长期需 `pt_order`、`pt_session` |
| `reservation.status` 无 `NOSHOW` 状态，且没有自动置位逻辑 | 出勤率、no-show 率、教练真实带课量全部偏高 | 定时任务在开课后 30 分钟把未签到的 `BOOKED` 置为 `NOSHOW` |

**这一节是后续所有报表的前置条件，优先级高于任何算法。**

**Mindbody**——排课是**配置驱动**而非算法驱动，公开文档写得很清楚：

- 课程容量可分开设 `online capacity`（线上可约数）与 `total capacity`（总容量），给 walk-in / 候补留位；

### 1.3 落地方案

#### A. 冲突检测（P0，半天）

**问题本质**：两段时间 `[s1,e1)` 与 `[s2,e2)` 重叠 ⟺ `s1 < e2 AND s2 < e1`。

现有唯一索引 `uk_schedule_slot (coach_id, class_date, start_time)` **只能防"开始时间完全相同"，防不住 10:00-11:00 与 10:30-11:30 的重叠**。而且完全没有 `room` 维度的约束。

**改造 1：重叠条件（常写错，务必对齐）**

```sql
-- 教练冲突
SELECT id, start_time, end_time, room
FROM course_schedule
WHERE class_date = #{classDate}
  AND status <> 'CANCELLED'
  AND coach_id = #{coachId}
  AND #{startTime} < end_time      -- 新开始 < 旧结束
  AND #{endTime}   > start_time;   -- 新结束 > 旧开始

-- 教室冲突：同样两个条件，把 coach_id 换成 room
```

**改造 2：数据库层兜底（可选，防并发/防脚本绕过）**

MySQL 没有 PostgreSQL 的 `EXCLUDE USING gist` 排除约束，只能用触发器兜底：

```sql
DELIMITER $$
CREATE TRIGGER trg_schedule_conflict_ins BEFORE INSERT ON course_schedule
FOR EACH ROW
BEGIN
    DECLARE cnt INT;
    SELECT COUNT(*) INTO cnt FROM course_schedule
     WHERE class_date = NEW.class_date
       AND status <> 'CANCELLED'
       AND (coach_id = NEW.coach_id OR room = NEW.room)
       AND NEW.start_time < end_time
       AND NEW.end_time   > start_time;
    IF cnt > 0 THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'CONFLICT: coach or room overlap';
    END IF;
END$$
```

> 触发器会把业务错误变成 SQLException，和现有 `BizException` 体系不兼容。**建议只做应用层校验 + 把 `uk_schedule_slot` 改成 `(coach_id, class_date, start_time)` 保留作为双保险**，触发器列为 P2 可选项。

**改造 3：Service 层伪代码**

```java
@Transactional
public void create(CourseSchedule req) {
    validateTimeRange(req);                     // end > start，且在同一天

    List<CourseSchedule> sameDay = list(new QueryWrapper<CourseSchedule>()
        .eq("class_date", req.getClassDate())
        .ne("status", "CANCELLED"));

    List<CourseSchedule> conflicts = sameDay.stream()
        .filter(s -> req.getStartTime().isBefore(s.getEndTime())
                  && req.getEndTime().isAfter(s.getStartTime()))
        .toList();

    // 冲突分类，给出可读的提示（店长最需要的是"跟谁撞了"）
    Optional<CourseSchedule> coachHit = conflicts.stream()
        .filter(s -> s.getCoachId().equals(req.getCoachId())).findFirst();
    if (coachHit.isPresent()) {
        throw new BizException("教练时间冲突：该教练 "
            + coachHit.get().getStartTime() + "-" + coachHit.get().getEndTime()
            + " 已有课程（" + coachHit.get().getRoom() + "）");
    }
    Optional<CourseSchedule> roomHit = conflicts.stream()
        .filter(s -> s.getRoom().equals(req.getRoom())).findFirst();
    if (roomHit.isPresent()) {
        throw new BizException("教室占用冲突："
            + roomHit.get().getStartTime() + "-" + roomHit.get().getEndTime()
            + " 该教室已被占用");
    }
    save(req);
}
```

**复杂度**：单日排课通常 <8 条，O(n) 过滤，实质 O(1)。即使不建索引也 <5ms。

**配套改造**：把 `room VARCHAR(30)` 提成 `room` 表（`id, name, capacity`），否则拼写不一致（"操房A" vs "操房 A"）会导致冲突漏检。这是**便宜且收益明确**的一步。

#### B. 时段需求分析（P1，半天）

不做预测，先做"历史需求画像"——店长自己能看懂的东西。

收缩均值（Shrinkage / 贝叶斯平滑），解决"某格只有 2 条记录、均值 100%"的失真：

```
fill_rate_smooth(g) = (n_g * fill_rate(g) + m * global_fill_rate) / (n_g + m)
```

- `g` = (course_type, day_of_week, hour_bucket) 分组
- `n_g` = 该格历史开课次数
- `m` = 平滑强度，取 5（相当于虚拟样本数）
- `global_fill_rate` = 全店历史加权满员率

```sql
-- MySQL 8：课程类型 × 星期 × 时段 的需求画像 + 收缩估计
WITH base AS (
    SELECT c.course_type,
           WEEKDAY(s.class_date) + 1  AS dow,          -- 1=周一
           HOUR(s.start_time)         AS hh,
           SUM(s.booked_count)        AS booked,
           SUM(s.capacity)            AS cap,
           COUNT(*)                   AS n_g
      FROM course_schedule s
      JOIN course c ON c.id = s.course_id
     WHERE s.status = 'FINISHED'
       AND s.class_date >= DATE_SUB(CURDATE(), INTERVAL 180 DAY)
     GROUP BY c.course_type, dow, hh
)
SELECT b.course_type, b.dow, b.hh, b.n_g,
       ROUND(b.booked / b.cap, 3) AS raw_rate,
       ROUND((b.n_g * (b.booked / b.cap) + 5 * g.global_rate)
             / (b.n_g + 5), 3)   AS smooth_rate      -- 收缩估计，m=5
  FROM base b
 CROSS JOIN (SELECT SUM(booked) / SUM(cap) AS global_rate FROM base) g
 ORDER BY smooth_rate DESC;
```

**输出给店长的话术**（比给数字有用得多）："周三 19:00 的搏击操近半年 12 次开课平均 92% 满员，建议加开一场；周四 14:00 瑜伽平均 28%，建议改到 20:00 或降价促销。"

#### C. 上座率预测（P2，1-2 天）

只在**排课页面做提示**："按历史，这个时段预计到 12±4 人"。方法同上（分组收缩均值），不需要模型。样本 <5 时**不显示预测**，只显示"暂无足够历史数据"——比给一个错数字好。

## 2. 预约与名额控制

### 2.1 现状：项目里已经做对了 70%

`ReservationService.reserve()` 第 69-76 行已经用了**条件更新（CAS）**：

```java
boolean locked = scheduleService.update(null, new UpdateWrapper<CourseSchedule>()
        .setSql("booked_count = booked_count + 1")
        .eq("id", scheduleId)
        .lt("booked_count", schedule.getCapacity()));
```

这是正确的路线——单条 `UPDATE ... WHERE booked_count < capacity` 由 InnoDB 行锁保证原子性，`affectedRows=0` 即"没抢到"。**不需要 Redis，不需要分布式锁，不需要 MQ。**

但这段代码有 4 个具体缺陷，都是真实会出问题的：

#### 缺陷 1：`capacity` 用了快照值，不是当前值

第 47 行 `getById(scheduleId)` 读出对象，第 73 行用 `schedule.getCapacity()`。如果店长在并发窗口内改了容量（放大或缩小），判断用的是旧值，**可能超卖或误拒**。

修复——直接比较列，而不是 Java 常量：

```java
boolean locked = scheduleService.update(null, new UpdateWrapper<CourseSchedule>()
        .setSql("booked_count = booked_count + 1")
        .eq("id", scheduleId)
        .apply("booked_count < capacity")     // 列 vs 列
        .eq("status", "WAITING"));            // 顺手防住已取消的课
```

#### 缺陷 2：取消后无法重新预约同一节课（唯一索引陷阱）

`schema.sql:208` 有 `uk_reserve_schedule_member (schedule_id, member_id)`，且取消是把 status 改成 `CANCELLED` 而**不删行**。而 `reserve()` 第 61-63 行的重复校验是 `status <> 'CANCELLED'`——于是：

> 会员预约 → 取消 → 再预约同一节课 → 重复校验通过 → INSERT 撞唯一索引 → `DuplicateKeyException` → 用户看到 500。

修复（二选一，推荐 A）：

**A. 复用行（推荐）**：取消时不写新行，重新预约时 UPDATE 原行 `status='BOOKED', reserve_time=NOW(), cancel_time=NULL`，同时做条件更新占名额。行数不膨胀，唯一索引反而成了并发重复预约的保底。

**B. 唯一索引改成部分索引**：MySQL 不支持部分索引，只能用 `(schedule_id, member_id, status)` 生成列技巧，代价是把一致性责任转移给了索引，且历史行会越积越多。不推荐。

#### 缺陷 3：名额和次卡次数没有联动

`reserve()` 里 `pickUsableCard()` 只是挑卡，**不校验次数、不扣次数**；扣次数发生在 `checkIn()`（第 155 行）。后果：

- 0 次余额的会员可以无限预约占坑，名额被"僵尸预约"占死；
- 签到那一刻才失败，会员已经到了店门口，体验极差。

修复：**预约时预扣**（或冻结），取消/未签到退回。

```java
// 预约：扣 1 次
boolean deducted = memberCardService.update(null, new UpdateWrapper<MemberCard>()
        .setSql("remain_times = remain_times - 1")
        .eq("id", card.getId())
        .gt("remain_times", 0));
if (!deducted) throw new BizException("次卡次数不足");
// 签到时不再扣（避免二次扣减），只更新 status
// 取消 / NOSHOW：退回 +1（NOSHOW 是否退次要按门店政策，建议不退）
```

期限卡（`end_date` 型）不需要预扣，只校验有效期。

#### 缺陷 4：取消时无条件归还名额

`cancel()` 第 116-118 行直接把 `booked_count - 1`。空出来的位置会被下一个点进来的人随手抢走，候补队列形同虚设。这一条在第 2.3 节解决。

### 2.2 并发方案选型对比

| 方案 | 实现成本 | 单店适用性 | 结论 |
|---|---|---|---|
| **A. 条件更新 CAS** | 极低，一行 SQL | 单行锁 1-2ms，支撑 500+ TPS | ✅ **采用**（现状已是） |
| B. `SELECT ... FOR UPDATE` | 低 | 把整节课串行化，事务持有锁到 commit，热点课会排队 | ❌ 不比 A 好 |
| C. 版本号乐观锁 | 中（要重试循环） | 高冲突下重试风暴，比 A 多一次读 | ❌ 多余 |
| D. Redis DECR 预扣 | 高（双写一致性、宕机补偿、对账） | 单店峰值 80 并发，用不上 | ❌ **不建议** |
| E. MQ / 队列削峰 | 很高 | 需要额外进程 + 结果回调 | ❌ **不建议** |
| F. `INSERT ... SELECT ... WHERE (SELECT booked_count) < capacity` | 中 | 原子性好，但可读性差，且与 A 等价 | ⚪ 可选 |

**容量实测口径**（给决策用，不是拍脑袋）：InnoDB 单行 UPDATE 在普通 SSD 服务器上约 0.5-2ms（含 fsync 由 `innodb_flush_log_at_trx_commit` 决定）。80 个并发请求排队 80×1.5ms ≈ 120ms 全部完成。**峰值响应 <200ms，用户体验无感。引入 Redis 只会把"120ms 完成"变成"50ms 完成 + 永久的一致性风险"。**

### 2.3 候补队列（P1，2-3 天）

#### 竞品做法

**Mindbody** 公开文档给出两种补位模式，这是本节最重要的参考：

- **Auto-add**：按加入候补的先后顺序，有人取消就自动把人加进名单，无需确认；
- **First to Claim**：发短信通知候补者，**第一个回复的人**被加入；
- 有 `waitlist lock window`（候补锁窗）：窗口内停止自动补位，交人工；
- 补位时若候补者**没有可用次数，系统跳过**他去通知下一个；
- 若候补者当天已约了别的课，可能被跳过（防止一人占多节导致爽约罚款）。
  来源：https://www.mindbodyonline.com/en-gb/business/education/product-waitlist-improvements
  来源：https://mindbodyonline.com/business/scheduling

**超级猩猩**：满员可加入候补队列，"排队成功会收到通知，需要及时确认预约"——属于 First-to-Claim 模式；开课前 6 小时外退课免费。

#### 伪代码（关键：不要引入 MQ）

```java
// 触发点：cancel() 成功之后。用 afterCommit 保证名额已经真正归还
TransactionSynchronizationManager.registerSynchronization(
    new TransactionSynchronization() {
        @Override public void afterCommit() { waitlistService.tryPromote(scheduleId); }
    });

public void tryPromote(Long scheduleId) {
    // 1. 还有空位吗？（用同一把 CAS，和抢课逻辑共用，天然防并发）
    CourseSchedule s = scheduleService.getById(scheduleId);
    if (s.getBookedCount() >= s.getCapacity()) return;

    // 2. 取队首
    Waitlist head = getOne(new QueryWrapper<Waitlist>()
        .eq("schedule_id", scheduleId).eq("status", "WAITING")
        .orderByAsc("position").last("LIMIT 1"));
    if (head == null) return;

    // 3. 资格校验：余次、当日冲突（抄 Mindbody 的 skip）
    if (!hasUsableCard(head.getMemberId())
        || hasOtherBookingSameDay(head.getMemberId(), s.getClassDate())) {
        skip(head.getId());        // status = SKIPPED
        tryPromote(scheduleId);    // 递归下一位，depth 受队列长度限制
        return;
    }

    // 4. 发通知（站内信/短信），置 NOTIFIED + 截止时间
    notifyWaitlist(head, confirmWindow(s));
}

// 兜底：定时任务每分钟扫一次，处理"通知超时"和"取消后事务没触发"的漏网
@Scheduled(cron = "0 * * * * ?")
public void expireAndCascade() {
    // 超时未确认 → EXPIRED，然后 tryPromote
    // 顺带扫 booked_count < capacity 且有 WAITING 的课，重新触发
}
```

**复杂度**：`tryPromote` 单次 O(1) 查队首 + 最多 O(k) 次顺延（k = 队列长度，实测 0-5）。无性能问题。

**注意**：递归在最坏情况（全员无次数）会栈深 = 队列长度。队列上限 100 也安全，但**建议改成 while 循环**，更稳。

#### 现有取消逻辑要改的地方

`cancel()` 里第 116-118 行的"直接 -1"要保留（必须归还），但**归还后必须触发 `tryPromote`**，否则空位会被随机路人抢走。

## 3. 推荐

### 3.1 竞品做法

- **Mindbody / ClassPass**：有推荐能力，但本质是**"附近 + 时间 + 品类"的筛选器 + 少量个性化排序**。ClassPass 的 SmartSpot 是"预测你会填不满哪些课"，属于**供给侧预测**，不是给会员的推荐。
  来源：https://classpass.com/partners/blog/classpass-smart-tools-helps-grow-revenue
- **乐刻**：宣传"千人千面的前期数据生成个性一体化运动方案"，但公开资料停留在愿景层面，**具体推荐算法未确认**。
- **超级猩猩**：应用商店描述有"根据上课频次与偏好自动生成个性化标签，系统据此推荐更适合的进阶课程"——即**标签/规则匹配**，不是协同过滤。来源：http://www.winwin7.com/azapp/249075.html （第三方应用站，可信度中等）
- **结论**：这个行业的"推荐"绝大多数是**规则 + 标签**，不是 ML。原因很简单——单店/单品牌的课程池只有 10-25 门，推荐的天花板本来就低。

### 3.2 小样本可行性判断（关键论证）

**协同过滤在这个数据量下不可行，理由是量化的，不是"感觉"：**

| 指标 | 数值 | 后果 |
|---|---|---|
| 用户数 × 课程数 | 300 × 20 = 6000 格 | 矩阵规模极小，但—— |
| 每人历史预约条数 | 中位数 ~35，但**只覆盖 5-8 门不同课程** | 用户向量稀疏度 **>60%** |
| 任意两门课的共现用户数 | 20 门课里，冷门课 × 冷门课的共现可能 **0-3 人** | Item-based CF 的余弦相似度分母趋零，算出来是噪声 |
| 任意两用户的共同课程数 | 多数用户对 **0-1 门** | User-based CF 的 Jaccard 相似度只有 0 和 0.5 两个值，无区分度 |
| 冷启动会员占比 | 新店/新会员常占 **15-30%** | CF 完全无法处理 |
| 评估难度 | 需要留出集、A/B，单店日活 <100 人 | 离线指标和线上效果都对不上，无法验证好坏 |

**反过来说，规则打分为什么可行**：

- 每个特征（类型偏好、教练偏好、时段偏好）都是**该会员自己历史上的占比**，样本 20-80 条足够稳定；
- 可解释——店长能看懂"因为您常上周三晚上的搏击课"；协同过滤给不出理由，店长不敢用；
- 冷启动有明确降级路径（回落到热度榜）；
- 出问题能立刻调权重，不用重训。

**结论：现在做规则打分，协同过滤列为"数据攒够再评估"（阈值建议：付费会员 >1000 且预约记录 >5 万条，此时 item-item 共现中位数能到 15+）。**

### 3.3 落地方案：加权评分 + 硬过滤

#### 第一步：硬过滤（必须）

```sql
候选课程 = 未来 7 天待开课的 schedule
  WHERE status = 'WAITING'
    AND booked_count < capacity
    AND 会员未预约过该 schedule
    AND 会员未在相同时段已有预约        -- 时间冲突
    AND 会员卡在该课日期仍有效
    AND 该会员尚未上过同一门 course（可选：避免重复推同一门）
```

这一步能砍掉 80% 的候选，剩下的才需要打分。

#### 第二步：加权评分

```
score(u, s) =
      w1 · 类型偏好   type(u, s.courseType)
    + w2 · 教练偏好   coach(u, s.coachId)
    + w3 · 时段偏好   slot(u, s.dow, s.hour)
    + w4 · 课程热度   heat(s.courseId)
    + w5 · 新鲜度     explore(u, s.courseId)
```

**各分项定义（全部归一化到 [0,1]，用 Laplace 平滑解决小样本）**：

| 分项 | 公式 | 说明 |
|---|---|---|
| 类型偏好 | `(n_type + α) / (N + α·K)`，α=1，K=课程类型总数 | n_type = 该会员预约过该类型的次数，N = 总预约次数。α=1 时新会员每类都得 1/K，自然回落到中性 |
| 教练偏好 | `(n_coach + α) / (N + α·C)` | 同上，C = 教练数 |
| 时段偏好 | `1 - |hour(s) - 会员到店时长中位数| / 12`，clip 到 [0,1] | 用中位数而非均值，抗单次异常。比按星期几匹配更稳（星期几样本太少） |
| 课程热度 | `percent_rank() OVER (ORDER BY 近30天fill_rate)` | 用分位数而不是绝对值，避免阈值调参 |
| 新鲜度 | 该会员没上过该课 → 1；上过 1-2 次 → 0.3；≥3 次 → 0 | 探索项，防止"越推越窄" |

**初始权重建议**：`w1=0.30, w2=0.25, w3=0.20, w4=0.20, w5=0.05`。
理由：类型和教练是会员最明确的偏好信号；热度保证新会员也能看到热门课；探索只留 5%，避免推荐"完全不相关但没上过"的课。

#### 第三步：计算实现（不做预计算表）

```java
// 会员 300 × 候选 15 = 4500 次评分，全内存 <5ms，每次请求实时算即可
public List<ScheduleVO> recommend(Long memberId, int topN) {
    MemberProfile p = profileService.build(memberId);   // 一次查询聚合出偏好向量
    List<CourseSchedule> cands = candidateQuery(memberId);   // 硬过滤 SQL

    return cands.stream()
        .map(s -> new Scored(s, score(p, s)))
        .sorted(Comparator.comparingDouble(Scored::score).reversed())
        .limit(topN)
        .map(this::toVO)
        .toList();
}
```

`MemberProfile` 一次 SQL 聚合：

```sql
SELECT r.member_id,
       c.course_type,
       c.coach_id,
       COUNT(*)                          AS cnt,
       AVG(HOUR(s.start_time))           AS avg_hour
  FROM reservation r
  JOIN course_schedule s ON s.id = r.schedule_id
  JOIN course c          ON c.id = s.course_id
 WHERE r.member_id = #{memberId}
   AND r.status IN ('BOOKED','CHECKED')       -- 不含 CANCELLED
 GROUP BY c.course_type, c.coach_id
```

单会员 <100 行，<10ms。

#### 第四步：教练推荐

比课程推荐更简单，规则即可：

```
coach_score(u, co) = 0.4 · 该教练在会员偏好类型上的历史复购率
                   + 0.3 · 教练档期与会员常到店时段的交集比例
                   + 0.3 · 教练近 30 天课程平均满意度/满员率
```

「复购率」= 上过该教练课的会员中，再次预约该教练的比例。这是单店最有效的教练质量代理指标（比评分更真实，因为有行为成本）。

## 4. 会员运营算法

### 4.1 竞品做法

- **乐刻**：宣传"根据门店位置、人流、用户画像等数据进行中心数据驱动排课"，会员侧有"完整的会员管理闭环，续费提醒"。其公开复购率数据：会员卡复购 70%、私教复购 45%（对比传统健身房 17.13% / 68.32%）。
  来源：https://sutt.suda.edu.cn/_s420/cb/dc/c23316a510940/page.psp
  注：这是论文引用的二手数据，口径未披露，**只能作为"行业有这么大差距"的量级参考，不要当基准线**。
- **三体云动（国内健身 SaaS）**：把流失预警的触发条件直接写成三个可操作维度——**储值卡剩余额度、次卡剩余次数、期限卡剩余时间**，"当会员成为即将流失的会员时及时联系"。
  来源：https://blog.styd.cn/big_data/368.html
  **这个做法比任何 ML 模型都实用**：它用"卡内余额/余次/剩余天数"作为流失的先行指标，因为这三者直接反映"沉没成本还剩多少"。
- **Mindbody / ClassPass**：有自动化营销（自动邮件、生日/到期提醒），但**是否用 ML 做流失预测未确认**，公开资料只有"automated reminders"层面的描述。

### 4.2 小样本可行性判断

| 方法 | 单店可行性 | 判断 |
|---|---|---|
| RFM 分位打分 | ✅ 完全可行 | 纯 SQL，300 人算 RFM 是教科书场景 |
| 规则型流失预警（间隔倍数法） | ✅ 最有效 | 见下，优于 ML |
| 逻辑回归流失预测 | ⚠️ 勉强 | 300 样本 × 5 特征可以拟合，但**需要 6-12 个月的标注数据**（谁真的流失了），且流失定义本身主观。ROI 不如规则 |
| 随机森林 / XGBoost | ❌ 过拟合 | 300 样本、正例（流失）可能只有 30-50 个，树模型必然过拟合 |
| K-means 会员聚类 | ❌ 不建议 | 能跑，但簇不稳定（换个月数据簇就变）、无法解释、运营动作和 RFM 高度重叠 |
| 到店频次异常检测（3σ / IQR） | ⚠️ 有条件可用 | 单会员历史 <15 条时 σ 不可靠，需改用绝对阈值 + 相对变化双条件 |

**核心判断：小样本下，"个人基线对比"比"群体模型"有效得多。**

原因：会员之间的到店频率差异是**结构性**的（有人每周 5 次，有人每月 2 次，都是正常）。用全店统一的"30 天未到店 = 流失"阈值，会把低频但忠诚的会员误判成流失，把高频会员的早期流失漏掉。而用**每个人自己的历史节奏做基线**，样本只要 10-20 条就够稳定，且天然个性化。

### 4.3 落地方案

#### A. RFM 分层（P0，0.5 天）

单店 R 最重要（F 和 M 高度相关：次卡按次消费，来得勤 = 花得多）。建议 **R、F 用五分位，M 用卡内余额**（因为单店消费额差异小，M 区分度低）。

```sql
-- MySQL 8，NTILE 五分位打分
-- 注意：不要用 LEFT JOIN reservation + member_card 再 GROUP BY，
--      一对多 × 一对多 会产生笛卡尔放大，SUM(remain_times) 被乘上预约条数。
--      用标量子查询，或先各自聚合再 join。
WITH base AS (
    SELECT m.id AS member_id,
           COALESCE(DATEDIFF(CURDATE(), (
               SELECT MAX(COALESCE(r.check_in_time, r.reserve_time))
                 FROM reservation r WHERE r.member_id = m.id
           )), 9999)                                              AS recency_days,   -- 无记录给大值，排到最旧
           (SELECT COUNT(*) FROM reservation r
             WHERE r.member_id = m.id
               AND r.status IN ('BOOKED','CHECKED')
               AND r.reserve_time >= DATE_SUB(CURDATE(), INTERVAL 90 DAY)) AS frequency_90d,
           (SELECT COALESCE(SUM(mc.remain_times), 0) FROM member_card mc
             WHERE mc.member_id = m.id AND mc.status = 'ACTIVE')   AS remain_times,
           (SELECT MAX(mc.end_date) FROM member_card mc
             WHERE mc.member_id = m.id AND mc.status = 'ACTIVE')   AS card_end_date
      FROM member m
)
SELECT member_id, recency_days, frequency_90d, remain_times, card_end_date,
       NTILE(5) OVER (ORDER BY recency_days ASC)   AS r_score,   -- 1=最近来过
       NTILE(5) OVER (ORDER BY frequency_90d DESC) AS f_score,   -- 5=最勤
       CASE
         WHEN card_end_date IS NULL                      THEN '无有效卡'
         WHEN card_end_date < CURDATE()                  THEN '已过期'
         WHEN DATEDIFF(card_end_date, CURDATE()) <= 30   THEN '即将到期'
         WHEN remain_times <= 2 AND remain_times > 0      THEN '余次不足'
         ELSE '正常'
       END AS card_state
  FROM base;
```

**分层矩阵（店长直接照着做动作）**：

| R | F | 命名 | 运营动作 |
|---|---|---|---|
| 高（近期来过） | 高 | **核心会员** | 不打扰。推私教/进阶课，做转介绍奖励 |
| 高 | 低 | **新客 / 养成期** | 推体验课 → 私教转化的黄金窗口，7 天内必须触达 |
| 低（久未到店） | 高 | **流失预警（高价值）** | **最高优先级**。电话回访 + 召回券。这批人一走损失最大 |
| 低 | 低 | **沉睡 / 僵尸** | 低成本触达（批量短信），不要浪费人力 |

这张表的价值在于：**把"低 R 高 F"单独拎出来**。这批人贡献过大量到店和收入，只是最近停了——正是最该打电话的 20 个人。

#### B. 流失预警：间隔倍数法（P0，1 天）

**核心公式**：

```
个人典型间隔  interval_median(u) = median(相邻两次到店的时间间隔)
当前间隔      gap(u)            = today - last_visit(u)
风险倍数      ratio(u)          = gap(u) / interval_median(u)

risk = HIGH    if ratio >= 2.5 and gap >= 14
       MEDIUM  if ratio >= 1.8 and gap >= 10
       LOW     else
```

**为什么用中位数不用均值**：单会员历史间隔里常有"出差 1 个月""受伤停练 2 个月"的长尾，均值会被拉高，导致该预警时不预警。中位数对这种污染免疫。

**为什么同时要 `gap >= 14` 的绝对下限**：周频会员的 interval_median ≈ 3.5 天，ratio 到 2.5 只有 8.75 天——对一周三练的人来说停 9 天不算异常（可能只是感冒）。加绝对下限能压掉这类误报。

**再加一层：卡状态加权**（抄三体云动的思路，这是国内最有效的信号）：

```java
int riskScore = 0;
if (ratio >= 2.5 && gap >= 14)        riskScore += 40;
else if (ratio >= 1.8 && gap >= 10)   riskScore += 20;

if (cardEndDate 距今天 <= 30)          riskScore += 25;   // 到期压力
if (remainTimes <= 2 && remainTimes>0) riskScore += 20;   // 次数快用完
if (cardEndDate 已过期)                riskScore += 35;
if (frequency90d >= 8)                 riskScore += 15;   // 高频会员流失代价高

// riskScore >= 55 → HIGH，35-54 → MEDIUM
```

**可解释性**：每条规则都能翻译成一句人话给会籍顾问："张先生平时每周来 3 次，已经 12 天没来了，卡还剩 2 次，下月 15 号到期"——这比"模型预测流失概率 0.73"有用一百倍。

**冷启动**：`interval_median` 需要至少 4 次到店记录。不足时**不输出预警**，只标"新会员，数据不足"。不要用全店均值兜底——那正是要避免的误判来源。

#### C. 续费预测（P1，0.5 天）

不做概率模型，做 **2×2 决策矩阵**（对店长更可用）：

| | 近 30 天到店 ≥ 4 次 | 近 30 天到店 < 4 次 |
|---|---|---|
| **剩余 ≤ 30 天** | 高续费意向 → **直接推续费，不要给折扣**（给了就是白送利润） | 低意向 → 先做体验挽回（约一次课），再谈续费 |
| **剩余 > 30 天** | 健康 → 推升级（次卡→期限卡、加私教） | 早中期风险 → 现在就该触达，别等到期 |

这个矩阵的价值：**避免"对所有到期会员都发折扣券"**。高频会员本来就要续，给他打折是纯损失；低频会员给折扣也多半不续，应该先解决"为什么不来"。

#### D. 到店频次异常检测（P2，0.5 天）

两个方向分开处理：

**异常降低**（可能流失 / 受伤 / 搬家）：同 B，用个人基线。

**异常升高**（可能是代刷 / 卡共享 / 数据错误）：
```
单日签到次数 >= 2           → 标记
同一会员相邻两次签到 < 30 分钟 → 标记
单周到店次数 > 该会员历史 P95 且 > 7 → 标记
```
这个信号对单店有实际价值：次卡被多人共用是行业常见漏洞。

**不要做的**：IQR 箱线图离群检测。单会员样本 <15 条时 Q1/Q3 估计不稳定，阈值会随数据抖动。用上面的绝对阈值组合更可靠。

## 5. 动态定价 / 营销

### 5.1 竞品做法（这是本节最有信息量的部分）

**ClassPass 是唯一公开了动态定价机制的玩家，且公开了效果数据：**

- **SmartRate**：按实时需求、季节性、可用性、出勤率、预约行为调整每节课的 credit 价格。"需求低时降价吸引预约，需求高或接近售罄时涨价，把最后几个位置卖贵"。同时设 **rate floor（保底价）**，按商家直客会员价的一定比例协商确定，保证不低于底线。
  来源：https://classpass.com/partners/blog/classpass-payouts-pricing-policies-rates
- **SmartSpot**：分析每个时段的**历史填充率**，只把"预测自己卖不掉的位置"释放给 ClassPass，避免侵蚀直客生意。
  来源：https://classpass.com/partners/blog/classpass-smart-tools-helps-grow-revenue
- **效果数据（官方口径）**：2024 年美国使用 SmartRate 的合作伙伴，ClassPass 结算额平均高约 **20%**，新客到访数翻倍以上，**满员率高约 14%**。
  来源：https://classpass.com/partners/blog/classpass-smart-tools-helps-grow-revenue
  第三方媒体转述同样数字：https://athletechstage.wpengine.com/classpass-tops-3-billion-in-partner-revenue
- **机制细节**：ClassPass 帮助页明确"同一节课不同周的 credit 数会变，取决于需求、距开课时间、促销"，**且是平台侧算法控制，商家不能自己设 credit 价**——这恰恰是商家最不满的点。
  来源：http://help.classpass.com/hc/en-us/articles/40825253236877-Why-do-class-credits-vary-from-week-to-week

**Mindbody**：本身是**静态定价**（price options / pricing tiers），动态定价能力是通过 ClassPass 外挂实现的。**自身是否有动态定价算法：未确认**，公开文档未见。

**乐刻 / 超级猩猩**：有次卡、课包、会员等级价、限时活动，但**是否有算法驱动的动态定价：未确认**。公开资料只到"营销活动"层面。

### 5.2 小样本可行性判断

| 子问题 | 判断 | 理由 |
|---|---|---|
| 实时动态定价（同一节课按需求变价） | ❌ **不建议** | ① 本项目**无支付模块**，变价无法闭环；② 国内健身用户对"同课不同价"接受度低，舆情风险高（ClassPass 自己就因为"平台控价"被商家长期诟病）；③ 单店每节课 10-20 人，价格弹性根本估不出来（需要几百次价格实验） |
| 淡时段折扣（规则驱动） | ✅ **强烈建议** | 这是 SmartSpot 的降维版：不是"动态变价"，而是"识别卖不掉的时段，对它定向促销"。规则固定、可解释、可随时关 |
| 次卡 vs 期限卡定价 | ✅ **可做测算工具** | 纯公式，不需要数据。帮店长算出"盈亏平衡到店次数" |
| 优惠券发放规则 | ✅ **可做，表驱动** | 和 RFM 联动，规则存表，不用规则引擎 |

### 5.3 落地方案

#### A. 淡时段折扣（P1，1 天）

**不做实时变价，做"提前 N 天的库存促销"**——本质是收益管理里的 early-bird，不改变挂牌价，只发定向券。

判定"淡时段"：

```sql
-- 未来 7 天内、距开课还有 3 天以上、但上座率仍低于 50% 的课次
-- 注意：start_time 是 TIME 类型，不能直接和 NOW()（DATETIME）比较，
--      必须用 TIMESTAMP(date, time) 组成 DATETIME 再比
SELECT s.id, s.class_date, s.start_time,
       s.booked_count, s.capacity,
       ROUND(s.booked_count / s.capacity, 2) AS fill_rate,
       (s.capacity - s.booked_count)         AS vacant
  FROM course_schedule s
 WHERE s.status = 'WAITING'
   AND s.class_date BETWEEN CURDATE() AND DATE_ADD(CURDATE(), INTERVAL 7 DAY)
   AND TIMESTAMP(s.class_date, s.start_time) > DATE_ADD(NOW(), INTERVAL 3 DAY)
   AND s.booked_count / s.capacity < 0.5
 ORDER BY fill_rate ASC;
```

**促销动作分级**（规则表，不进代码）：

| 剩余空位占比 | 距开课 | 动作 |
|---|---|---|
| >60% 空 | ≥3 天 | 全员可见"限时 X 折"，不限人群 |
| 40-60% 空 | 1-3 天 | 仅对 RFM「沉睡」「新客」发放 |
| <40% 空 | <1 天 | 不动。降价也卖不掉，还稀释品牌 |

**关键约束**：折扣**只针对次卡/单次购买**，不能影响期限卡会员的权益感知；且同一课程类型每周最多促销 1 次，否则会员会养成"等打折"的习惯（这是收益管理里最经典的坑）。

#### B. 次卡 vs 期限卡：盈亏平衡到店次数（P0，半天，纯公式）

这是本节**投入产出比最高**的东西——一个 Excel 级别的公式，直接指导定价。

```
设：
  期限卡价格  P_period（如月卡 299 元）
  单次价格    P_visit （如单次 60 元）
  期限卡有效期 T（月）

对会员而言的盈亏平衡次数：   N* = P_period / P_visit
   （即：一个月来 N* 次以上，买期限卡才划算）

对门店而言的毛利率约束：
   期望毛利 = P_period - N_expected × 边际成本(单次场地/人力)
   其中 N_expected = 该卡种历史会员的实际月均到店次数

定价原则：
   令 N* 略高于 N_expected（如 N* = 1.2 × N_expected）
   → 会员觉得"差不多划算"，门店不会因为高频用户亏本
```

**实例**：单次 60 元，会员月均到店 8 次。若月卡定 299，N*=4.98，会员来 8 次就"赚了"3 次——**门店在补贴高频会员，且会吸引"专薅羊毛"的用户**。若月卡定 580，N*=9.67，比实际均值高，会员会算账后转次卡。

**建议区间**：`P_period ∈ [N_expected × P_visit × 0.75, N_expected × P_visit × 0.9]`，即给会员 10-25% 的"预期折扣"，既能体现期限卡的性价比，又不至于被高频用户吃穿。

这个公式要落成一个小工具（输入 3 个参数，输出建议价区间），不需要存表。

#### C. 优惠券规则（P2，1-2 天）

**不做规则引擎（Drools 太重），做表驱动**：

```sql
CREATE TABLE coupon_rule (
    id           BIGINT PRIMARY KEY AUTO_INCREMENT,
    rule_name    VARCHAR(50)  NOT NULL,
    -- 触发条件
    segment      VARCHAR(20),          -- RFM 分层：CORE/NEW/DORMANT/AT_RISK，NULL=不限
    min_recency  INT,                  -- 距上次到店天数下限
    max_recency  INT,
    min_freq_90d INT,
    card_state   VARCHAR(20),          -- EXPIRING / EXHAUSTED / EXPIRED
    -- 动作
    coupon_type  VARCHAR(20) NOT NULL, -- DISCOUNT / FREE_TRIAL / GIFT_TIMES
    face_value   DECIMAL(8,2),
    valid_days   INT NOT NULL DEFAULT 7,
    priority     INT NOT NULL DEFAULT 0,
    status       TINYINT NOT NULL DEFAULT 1,
    create_time  DATETIME NOT NULL
);
```

匹配逻辑：**从上到下取第一条命中的规则，一人一次只发一张**（避免叠加）。这比"评分择优"更符合实际运营——店长只想控制"什么人拿什么券"，不想调权重。

**规则示例**：

| segment | 条件 | 动作 |
|---|---|---|
| AT_RISK | recency 15-45 天 且 freq_90d ≥ 6 | 免费私教体验 1 次（不是折扣券——高价值流失者需要的是"理由回来"，不是便宜） |
| DORMANT | recency > 45 天 | 5 折单次券，7 天有效 |
| NEW | 入会 ≤ 30 天 且 freq < 4 | 第 2 次到店送 1 次（培养习惯，不是刺激消费） |
| EXPIRING | card_state = EXPIRING 且 freq_90d ≥ 8 | **不发券**，直接推续费（发了纯亏） |

最后一条是重点：**"不发券"也是一个规则**。

## 6. 数据看板指标

### 6.1 指标定义（含口径陷阱，这部分比公式本身重要）

> 说明：行业基准区间来自国内健身 SaaS（三体云动）与行业知识库的公开整理，**不同城市/店型/卡种结构差异极大，只能做"内部趋势对比"和"量级判断"，不可对外承诺**。
> 来源：https://blog.styd.cn/big_data/368.html ；https://skillsmp.com/zh/creators/deepleaper/leaper-agent/skills-skills-l1-industry-fitness （后者为 AI 知识库整理，权威性有限，仅作量级参考）

| # | 指标 | 定义与公式 | 口径陷阱 | 数据来源 | 参考量级 |
|---|---|---|---|---|---|
| 1 | **月到店率** | 当月有 ≥1 次入场记录的会员数 ÷ 当月有效会员数 | ① 分母必须是"卡在有效期内"，不是"会员总数"；② **必须有自由训练入场记录**（见 0.1），否则只统计团课会员，数值偏低 30%+ | `checkin_log` + `member_card` | 40-60% |
| 2 | **满员率** | `Σ booked_count ÷ Σ capacity`（**按课次加权**） | ① 不能用"平均每节课的满员率"（简单平均），3 人小课和 30 人大课权重不同；② 是否含候补要声明；③ 用 booked 还是实到，是**两个不同指标** | `course_schedule` | 60-80%（团课） |
| 3 | **出勤率 / No-show 率** | 出勤率 = 实到人数 ÷ 预约人数；No-show = 1 − 出勤率 | 依赖 `reservation.status` 有 `NOSHOW` 且自动置位。现在没有 → 现在算出来的出勤率**必然虚高**（未签到的不计入分母） | `reservation` + 定时任务 | No-show 5-15% |
| 4 | **续费率** | 观察期内到期会员中，到期后 X 天内产生新卡/续费的占比 | ① 必须固定观察窗口 X（建议 30 天），否则各月不可比；② "续费"是同类卡还是任意卡，要区分；③ 分母是"到期人数"不是"到期卡数"（一人多卡会重复） | `member_card` + `card_recharge` | 年卡 30-50%，月卡 60-75% |
| 5 | **私教渗透率** | 购买过私教的会员数 ÷ 总有效会员数 | **别和"转化率"混用**。渗透率是存量口径，转化率是流量口径 | 需新增 `pt_order` | 15-30% |
| 5b | **私教转化率（真正意义的）** | 体验课后 30 天内购买私教的人数 ÷ 体验课人数 | 这是业务上真正关心的那个数。用渗透率代替会严重高估销售能力 | 需 `pt_trial` 记录 | 20-40% |
| 6 | **坪效** | 月营业收入 ÷ 门店使用面积(㎡) | ① "使用面积"还是"建筑面积"要统一；② 分子含不含私教、商品，口径要固定，否则跨月不可比 | 需新增面积字段 | 300-600 元/㎡·月（社区店偏上限，大店偏下限） |
| 7 | **会员流失率** | 流失人数 ÷ 期初会员数；或 `((ME − MN) / MS) × 100%`（ME=期末数，MN=期内新增，MS=期初数） | 第二个公式是行业标准算法，来源：https://www.chinafit.com/news_spe_view.php?type=sv&sid=&id=38502 （引 Paul Bedford 的方法）。注意"冻结/请假"会员要单列，算流失会把停卡的人错算进去 | `member_card` + `member` | — |
| 8 | **课消率** | 已上课时 ÷ 已购课时 | 私教的核心健康指标。低于 70% 意味着大量预收款是负债，有跑路风险 | 需 `pt_session` | 70-85% |
| 9 | **教练课时利用率** | 实际授课时长 ÷ 可排课时长 | 分母定义要明确（按 8 小时工作制还是按可排时段） | `course_schedule` + `coach` | 50-70% |
| 10 | **会员月均到店频次** | 总签到次数 ÷ 月活会员数 | 用月活做分母（不是总会员），否则被沉睡会员稀释 | `checkin_log` | 4-8 次 |
| 11 | **客单价 / ARPU** | 月营收 ÷ 月活会员数 | — | `card_recharge` | — |
| 12 | **CAC** | 期间营销费用 ÷ 期间新增会员数 | 单店常漏算人力成本（会籍工资），会显著低估 | 需费用录入 | — |

### 6.2 落地建议

**先直查，别预聚合。** 单店 `reservation` 一年 1-4 万行，`GROUP BY` 全表 <50ms。加物化表反而带来"数据不一致 + 重算逻辑"的维护成本。

```sql
-- 满员率（按课次加权，含口径说明）
SELECT DATE_FORMAT(s.class_date, '%Y-%m')                AS month,
       COUNT(*)                                          AS class_cnt,
       SUM(s.booked_count)                               AS total_booked,
       SUM(s.capacity)                                   AS total_capacity,
       ROUND(SUM(s.booked_count) / SUM(s.capacity), 3)   AS fill_rate_weighted
  FROM course_schedule s
 WHERE s.status = 'FINISHED'
   AND s.class_date >= #{start} AND s.class_date < #{end}
 GROUP BY month;
```

**什么时候才需要物化**：当 `reservation` 超过 50 万行（约 10-15 年单店数据）或看板需要秒开且含多表 join 时，再加 `daily_stat(stat_date, metric_key, metric_value)`，用 `@Scheduled` 每天凌晨跑一次。**现在不需要。**

**看板设计原则**（比指标数量重要）：
- 首页只放 **4 个数字**：今日到店、本周满员率、本月续费率、待处理预警数。
- 每个指标都要能点进去看"构成"（哪些会员、哪些课），否则店长不会信。
- 所有比值类指标**同时显示分子分母**（"满员率 72%（1,240 / 1,720）"），否则无法判断是小样本波动还是真趋势。

## 8. 「不建议做」清单及理由

### 8.1 协同过滤推荐（item-CF / user-CF）

**理由（量化）**：300 会员 × 20 课程，任意两门课的共现用户中位数在 0-3 之间。余弦相似度的分母趋近 0，算出来的"相似度"是噪声。User-CF 更糟：两个用户的共同课程数多为 0-1，Jaccard 只有 0 和 0.5 两个取值，排序失去意义。

**替代方案**：规则加权打分（3.3）。**重新评估的阈值**：付费会员 >1000 且累计预约 >5 万条，此时 item-item 共现中位数可达 15+。

**额外成本**：CF 需要离线训练 + 相似度矩阵存储 + 冷启动处理 + 效果评估体系，合计 3 天以上，而单店课程池只有 20 门——**推荐的天花板本来就低**，投入产出不成比例。

### 8.2 自动排课优化器

**理由**：

1. **真实约束无法形式化**：教练只想上某类课、住得远只能上早班、某教练是兼职只能周末、商场 22:00 断电、某门课版权方要求每周固定时段。这些写不进目标函数，硬写就要 20+ 个硬约束，求解器会告诉你"无可行解"。
2. **NP-hard 且单店规模下无必要**：单店一周 20-45 节课、3-8 个教练，人工排课 1-2 小时能完成且质量可接受。引入求解器（OR-Tools / Timefold）需要额外进程 + 约束建模 + 调参，**成本远超收益**。
3. **信任问题**：店长不会接受一个黑盒课表。乐刻能做是因为中心化调度 + 500 店的数据量，且即便它自述准确率也只有 80%。
4. **数据不足**：要训练/验证排课效果，需要"同一时段排不同课"的对照实验，单店根本做不出样本量。

**替代方案**：冲突检测（1.3-A）+ 历史需求画像（1.3-B）+ 一键复制上周课表。把"排课"从"生成问题"降级为"校验 + 参考问题"——这是 Mindbody 和乐刻店管家都在做的事。

### 8.3 实时动态定价

**理由**：

1. **本项目无支付模块**，变价无法闭环到交易，做了也是空转。
2. **价格弹性和样本量不匹配**：要估计一节课的价格弹性，需要在相似条件下做几十次价格实验。单店每节课 10-20 人、每周 1 次，**一年也攒不够一次可信实验**。
3. **用户接受度风险**：ClassPass 因为"平台控制 credit 价格、商家无法自主"被商家长期批评（来源：https://rapidevelopers.com/clone/classpass 的批评汇总；以及 ClassPass 帮助中心承认价格由平台算法决定）。国内单店做同课不同价，等于主动制造投诉素材。
4. **收益不确定，损失确定**：让老会员发现自己比邻座贵 20 元，损失的是一个会员而不是一单生意。

**替代方案**：淡时段定向折扣（5.3-A）。保持挂牌价稳定，只对"确定卖不掉的库存"做定向促销——这是 SmartSpot 的思路，风险低得多。

### 8.4 Redis 预扣名额 / MQ 削峰

**理由**：

1. **算不过账**：80 并发 × 1.5ms 行锁 = 120ms 全部完成。Redis 能把 120ms 优化到 50ms，**但用户感知不到差别**（人的感知阈值 ~200ms）。
2. **引入一致性问题**：Redis 扣减 + MySQL 落库 = 双写。宕机、过期、主从延迟、补偿对账，每个都是新 bug 来源。为了"不存在的性能问题"引入"必然存在的一致性问题"，是典型的负收益。
3. **运维成本**：单机部署的 Spring Boot 加一个 Redis 进程，意味着部署文档、监控、备份、故障预案全部翻倍。
4. **条件更新已经足够正确**：`UPDATE ... WHERE booked_count < capacity` 是数据库层面的原子操作，正确性有保证。

**唯一值得考虑 Redis 的场景**：日活 >5000 或出现跨店共享名额（多店抢同一批库存）。单店不存在。

### 8.5 ML 流失预测 / 会员聚类

**理由**：

- **标注不足**：300 会员，真实流失（期限内不再续费且 90 天不到店）可能只有 30-50 例。逻辑回归 5 个特征勉强能拟合，但**置信区间宽到无法决策**；树模型在这个样本量下必然过拟合。
- **定义本身主观**："流失"依赖观察窗口选择（30/60/90 天），换个窗口结论就变——模型学的是窗口定义，不是用户行为。
- **规则已能达到同样效果**：间隔倍数法（4.3-B）的可解释性、可调性、冷启动表现都优于模型，且当天就能上线。
- **聚类更差**：K-means 在 300×3 维上能跑，但① 簇数 K 无客观依据；② 换个月数据簇就漂移；③ 输出的簇和 RFM 四象限高度重叠，**没有增量信息**；④ 无法向店长解释"为什么这个人是第 3 簇"，运营动作落不了地。

**替代方案**：RFM 分位 + 间隔倍数 + 卡状态加权（4.3）。这三者的组合已经覆盖了 ML 能提供的全部可执行信息。

### 8.6 其他

| 项 | 理由 |
|---|---|
| 视频动作识别 / 体测数据自动判读 | 需要 CV 模型 + GPU + 大量标注。与"管理系统"定位无关，且单店无训练数据 |
| 多店横向对比 / 店间坪效排名 | 单店无对比对象。数据结构可以为将来留扩展（`store_id`），但功能不做 |
| 完整推荐系统平台（召回-粗排-精排） | 候选集只有 15-20 条，**粗排精排的工业级架构在这里是纯浪费**，一次全量打分 <5ms |
| 消息推送系统（本项目无此模块） | 需求已声明不做。但需注意：候补补位通知（2.3）依赖站内信，如果用短信要评估成本 |

## 10. 一页纸总结

**这个系统的算法含量被高估了。** 六个方向里，真正需要"算法"的只有第 3、4 节，而它们的最优解都是**规则 + 统计量**，不是机器学习。原因不是"技术不够"，而是**单店的数据量（300 会员 / 20 门课 / 年 1-4 万条预约）在数学上就不支持复杂模型**。

按投入产出排序，真正该做的五件事：

1. **修 3 个数据正确性 bug**（capacity 快照、唯一索引导致无法重约、缺 NOSHOW 状态）—— 0.9 天，价值最高，因为**错误的数据会污染所有下游指标**。
2. **补 1 张 `checkin_log` 表** —— 0.5 天，没有它，"到店率""月活""坪效"全是错的。
3. **冲突检测 + 一键复制课表** —— 0.8 天，排课模块从"能用"到"好用"。
4. **RFM + 间隔倍数流失预警** —— 2 天，直接产生可执行的会员名单，店长第二天就能打电话。
5. **候补队列** —— 2-3 天，满员率提升最直接的杠杆（业界案例：71% → 88%）。

明确不做的四件事：协同过滤、自动排课优化器、实时动态定价、Redis/MQ。

**判断标准很简单**：如果一件事需要"更多数据"才能验证效果好，而单店拿不到那么多数据，那它就不该做——不是现在不做，是这个场景下永远不该做。
